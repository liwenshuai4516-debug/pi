# 验收与能力边界

## 新项目的分层验收

1. 安装检查：运行 doctor，确认版本、10 个工具定义、阶段 Skills/评估规则、契约正反例、临时存储往返及 Chromium 启动。它不访问目标站点或模型，也不证明宿主已接好扩展。
2. 宿主检查：新会话真实发现8个阶段 Skills与10个工具，调用 catalog；浏览器录制时另确认7个关键测试 MCP 工具和取消能力。缺项保持 blocked，不换成假工具。
3. 最小业务闭环：选择一个允许的可清理主链，真实录制或有来源发现 → case/断言 → 独立设计评估 → 正反诊断 → 正式新批次 → 确定性分析 → 独立结果评估。保存真实证据，不用受控模型响应声称模型规划已通过。
4. 复用：完全退出宿主后新会话执行同一有效资产；应新建 run、重新预检，且没有不必要的录制/设计调用。对旧 run 的 analyze/view 不应增加业务请求。
5. 失败与边界：用隔离故障副本验证实际失败可被报告；未知根因保留 unknown；失败重跑只改变新子批次，原失败摘要不变。登录过期、缺证据和未知写入须阻断或诚实 partial。

模型更换或新业务投入使用时，用有确认标签的合理/错误断言及无依据归因样本验证两个 reviewer。原项目的校准结果不能代替目标模型/业务验收。不要为了复现原项目校准而访问原账号或批量重发未知业务动作。
